## Принятые решения

1. **Паттерн Order / OrderLine** — модель данных Booking строится как Request (шапка) + RequestItems (позиции) + Bookings (подтверждённые брони). Это явная доработка к `2026-04-08 - Архитектура БД базовая.md`, где `request_items` не была выделена как самостоятельная сущность.

2. **Статус-машина на двух уровнях:**
   - Request — агрегированный статус (`draft → submitted → partially_confirmed → fully_confirmed → in_progress → completed`)
   - RequestItem — атомарный статус (`pending_fo → confirmed / rejected / cancelled`)
   - Booking — статус жизни брони (`confirmed → in_progress → completed / cancelled`)

3. **Период запрошен на уровне Request** (окно Requestor-а), **фактический период — на уровне RequestItem/Booking** (может уточняться FO при подтверждении).

4. **Место доставки и транспорт — атрибуты RequestItem**, не шапки Request (каждая единица может ехать в разное место).

5. **Booking хранит только ID** — данные техники и пользователей живут в модуле Resources. Booking = координирующий bounded context.

6. **Snapshot техники в Booking** — рекомендовано (не финализировано): сохранять ключевые поля техники на момент подтверждения для читаемости истории.

7. **statusHistory[] как embedded array** в Request/Booking — для отображения timeline в UI без JOIN (в дополнение к `audit_logs`).

8. **Conflict-check** на уровне RequestItem (не Request): проверять доступность при создании позиции.
