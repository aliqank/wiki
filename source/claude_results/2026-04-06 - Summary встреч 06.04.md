### Что обсуждали

#### Валидация BPMN v2
Команда провела walk-through обновлённой схемы процесса бронирования (equipment request process v2.bpmn). Схема была показана заказчику для выравнивания.

**Подтверждённая логика процесса (как договорились):**

```
Requestor: выбирает тип техники → указывает период → выставляет приоритет → сабмитит

Система:
  → проверяет наличие во внутреннем парке
  → [есть] → публикует Internal FO → ждёт 24ч
     → 24ч без ответа → reminder
     → 48ч без ответа → эскалация на External
  → [нет] → открывает Justification window для Requestor

FO принял решение:
  → Confirm + назначил технику + мобилизовал
     → система уведомляет Requestor (confirmed)
     → процесс уходит в оффлайн
  → Reject (с обязательным комментарием)
     → заявка остаётся для других Internal FO (не пропадает!)
     → если все отказали → эскалация на External
```

**Ключевое уточнение по rejection:**
> Если FO отказал при наличии свободной техники — **обязан написать причину**. Система не закрывает заявку — она остаётся видной остальным внутренним FO.

#### Тайм-аут Fleet Owner
Зафиксировано: **24 часа** — заявка ждёт ответа внутреннего FO. Без ответа — переход на внешний флот. Параметр настраиваемый.

#### Статус DCT

### 1. Ключевое открытие: три категории внешней техники

**Ирлан** ввёл чёткую классификацию, которая ранее не была явно артикулирована:

| Категория | Описание | Нужна ли новая авторизация? | Процесс |
|-----------|----------|----------------------------|---------|
| **1 — Собственная (TCO)** | Техника в собственности ТШО | Нет | Стандартный Internal FO flow |
| **2 — Долгосрочная аренда (рентед)** | Техника BP, арендованная ТШО на длительный срок (например, 10 Hiace); ТШО уже оплачивает её по контракту | Нет — распоряжаться может сам Fleet Owner | Аналогичен внутреннему флоу |
| **3 — On-demand (без авторизации)** | Техника BP, которая привлекается под конкретную задачу; требует проведения лёгкого тендера (light bid) и выпуска нового SR | Да — процесс через DCT или контрактную группу | Сложный — требует отдельного флоу |

**Практический пример (Ирлан):**
> "Вот у меня есть 10 Hiace. Я им плачу каждый месяц за каждый день. Хочу — делюсь с другим отделом, потому что я уже заплатил. Здесь никакой авторизации не нужно. Это как внутренняя техника."

**Зафиксировано на встрече:** фокус Phase 1 — **Категории 1 + 2**. Категория 3 — следующий этап после привлечения контрактной команды.

### 2. DCT — демонстрация и обсуждение (Светлана Курбети)

Светлана показала тестовую среду DCT. Ключевые факты о системе:

| Параметр | Описание |
|----------|----------|
| **Цель DCT** | Создание и ведение Work Authorizations (RWA) + формирование таймшитов → инвойсов |
| **RWA (Work Authorization)** | Содержит: тип работ, Cost Center (IF), ресурсы по категориям (manpower, equipment), start/end date |
| **Бидинг** | Несколько BP выбираются в одну RWA; каждый отправляет ценовое предложение независимо (не видит чужие ставки) |
| **Ставки** | Прописаны в контракте, BP не может отклоняться от них |
| **Конфиденциальность** | Инициатор видит только **общую сумму**, но не юнит-ставки |
| **SR (Service Request)** | Создаётся в SMART после выбора BP; к нему привязываются все затраты и таймшиты |
| **Конфликт с Booking Tool** | В DCT — тендерный процесс (сравниваются несколько BP); в Booking Tool предполагается, что FO сам откликается на заявку |

### 3. Предложенный флоу для Категории 3 (Турсынбек)

После обсуждения сформировался **консенсусный вариант**:

```
Requestor → заявка не нашла техники в Категориях 1 и 2
       ↓
Booking Tool уведомляет → Requestor нажимает "Поиск у бизнес-партнёров"
       ↓
Заявка направляется Контрактному специалисту (Central Contract Group)
       ↓
Специалист проводит процедуру вне системы (DCT, переписка, лайт-бид)
Получает от BP: общая сумма + дата мобилизации
       ↓
Специалист заносит результаты в Booking Tool:
  Бидер 1: сумма, дата
  Бидер 2: сумма, дата
  Бидер 3: сумма, дата
(без названий компаний, если нужна конфиденциальность)
       ↓
Requestor выбирает оптимальный вариант
       ↓
Выбор уходит к Контрактному специалисту → он выпускает SR в DCT/SMART
       ↓
SR-номер возвращается в Booking Tool → бронирование активируется
```

### 4. Каталог техники бизнес-партнёров

Обсуждалась концепция **единого каталога карточек техники BP**:

- Одна стандартная карточка для каждого типа техники (без дублей от разных BP)
- BP подтверждают, что у них есть соответствующая техника (без ставок)
- Контрактный специалист, открывая карточку, видит список BP с этой техникой
- BP могут указывать занятость техники по датам → Requestor видит доступность
