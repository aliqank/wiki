### Контекст
Прохождение обязательной процедуры оценки рисков приложения (ACR) для получения тира безопасности.

### Результаты оценки

| Параметр | Значение |
|----------|---------|
| **Тир риска** | **Low** (низкий) |
| Тип приложения | In-house, .NET/Angular, Azure PaaS, MongoDB |
| PII / Sensitive data | ❌ Не содержит |
| GDPR/CCPA применимость | ❌ Не применимо |
| SOX (ценные бумаги) | ❌ Не является торговым приложением |
| Финансовый импакт при падении | Minimal — команды переходят на ручной режим (Excel), как сейчас |
| Репутационный риск | Минимальный — ценовые данные в системе отсутствуют |
| Число пользователей | ~200 (оценка; 0–200 диапазон) |

### Что хранится в системе
- Технические характеристики техники: тип, серийный номер, номер шасси, статус, класс, локация
- Cost Center, департамент, Fleet Owner контакты
- Статус доступности (занято / свободно)
- **НЕ хранится: ценовые ставки, компенсации, персональные данные**

### Подтверждено: ценовые данные не отображаются
Явно подтверждено: **прайсинг в систему не выводится** — ни для внутренней техники, ни для BP. Полный ценовой процесс остаётся в DCT/SMART/контрактной системе.

### Статус
- Оценка заполнена; ожидается **approve от Светланы** → система получает официальный тир
- После approve — список контролей безопасности

### Интеграции (подтверждено)
JDE E1, PSWS (PS) — данные отправляются в сторонние системы (указано как Yes в ACR-форме)

### Блок B — Контрактная команда: Cat 3 и DCT

#### ❗ КРИТИЧЕСКИ ВАЖНЫЕ УТОЧНЕНИЯ

**1. DCT (десяти/10ти) — ограниченный доступ**
> DCT может использовать **только Routine Maintenance и Major Maintenance**.
> Логистика, Projects, Construction и другие департаменты — **не имеют права использовать DCT**.
> Для этих департаментов существует **Central Contract Group (CCG)** — делает light bid проверки по всем категориям.
> Отдельная группа — для Projects/Construction/Engineering (своя команда CCG).

**2. Использование техники BP — только из действующих контрактов**
> Техника BP, **не включённая** в действующий контракт, **НЕ может быть использована**:
> - нельзя забронировать ad-hoc
> - требует полного тендера (ценовые предложения от всех провайдеров) + доп. соглашения к контракту
> - только после добавления в контракт — техника может использоваться

**3. Три категории BP equipment (уточнение Cat 2 / Cat 3)**

| Категория | Описание | Процесс бронирования |
|-----------|---------|---------------------|
| Cat 1 | TCO собственная техника | Direct → FO |
| Cat 2 | BP техника **в действующем контракте** (долгосрочный контракт, multi-year) | Direct → FO (BP) через контракт |
| Cat 3 | BP техника **вне контракта** / новая | Требует тендер → доп. соглашение → только потом доступна в системе |

**4. Рекомендация Balkindge — поле "статус в контракте"**
> В карточке BP-техники добавить два флага:
> - ✅ Included in contract — можно бронировать через Booking Tool
> - ❌ Out of contract — нельзя бронировать; нужен новый тендер

**5. Scope Phase 1**
- Phase 1: Cat 1 + Cat 2 (подтверждено)
- Cat 3 (вне контракта): скорее всего **Phase 2** (требует полной контрактной процедуры)

## Встреча 4 — Requirement Gathering (основная)
**Время:** ~16:01

### Блок A — Процесс бронирования: КАРДИНАЛЬНОЕ ИЗМЕНЕНИЕ МОДЕЛИ

#### ❗ ПЕРЕСМОТР АРХИТЕКТУРЫ ПРОЦЕССА

**Старая модель (BPMN v3):** Requestor указывает тип техники → система делает broadcast на всех FO с данным типом → первый отреагировавший FO берёт заявку.

**Новая модель (решение 07.04):** Requestor видит конкретные единицы техники и сам выбирает конкретную единицу у конкретного FO → целевой запрос идёт этому FO.

> 🔴 **Зафиксировано:** «Реквестер выбирает в конкретном флите конкретный equipмент, чтобы на него отправить бронь.»

| Шаг | Новое поведение |
|-----|----------------|
| 1 | Requestor фильтрует доступную технику (только Shared / SWC статусы) |
| 2 | Видит конкретные единицы с техническими характеристиками |
| 3 | Выбирает конкретную единицу → отправляет запрос конкретному FO |
| 4 | FO: подтверждает → бронирование активно |
| 5 | FO: отказывает → заявка возвращается в статус "выбора техники"; Requestor выбирает другую единицу |
| 6 | Заявка НЕ закрывается при отказе — остаётся открытой у Requestor-а |

### Блок B — Жизненный цикл бронирования

| Вопрос | Решение |
|--------|---------|
| **Кто завершает бронирование?** | **Либо Requestor, либо FO** — кнопка "Завершить/закрыть бронь" у обоих. При закрытии — техника автоматически становится доступной. |
| **Продление брони** | Кнопка "Extend booking". Запрос уходит FO. FO видит, есть ли следующая бронь. FO может принять или отказать. |
| **FO получил два запроса (продление vs следующая заявка)** | FO сам принимает решение: отказывает продлению ИЛИ перекидывает следующую заявку |
| **No-show (Requestor не вышел, но техника приехала)** | Считается "в работе" — FO не виноват; заявка не закрывается автоматически |
