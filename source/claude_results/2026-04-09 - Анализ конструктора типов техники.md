# Анализ идеи: конструктор типов техники и характеристик
**Дата:** 2026-04-09  
**Тип документа:** Архитектурный анализ  
**Источник:** «Рассуждение на тему типов техники и параметров для фильтра.md»  
**Контекст:** Матрица фильтров (37 активных типов), Архитектура БД v1, Master Fleet File (786 единиц)

---

## Суть идеи (как понята)

FO получает конструктор:
1. Создаёт тип техники → задаёт уникальные характеристики (название + ед. измерения)
2. Характеристики сохраняются в справочник и переиспользуются между типами
3. Галочка «показывать в фильтрах» контролирует видимость в поиске Requestor-а
4. При добавлении конкретной единицы техники — поля генерируются автоматически из характеристик типа

---

## Оценка: реалистичность и реализуемость

### Концептуально — да, паттерн рабочий

Это классический **EAV (Entity-Attribute-Value)** или **dynamic schema** подход. Его используют CRM-системы, Service Desk-платформы, asset management системы. Концепция проверена и реализуема.

**Что в идее хорошего:**
- Переиспользование характеристик через справочник — правильно
- Галочка «в фильтрах» — именно это нужно для динамической матрицы
- Отвязка FO от разработчиков при появлении нового типа — ценно

---

## Риски и проблемы

### Риск 1 — Противоречие с реальностью проекта ⚠️ ВЫСОКИЙ

**Типы техники уже известны.** Из Master Fleet File получено **37 активных типов** + 8 deprecated. Атрибуты для каждого типа уже описаны в матрице фильтров. Это не TBD — это зафиксированные данные.

> Конструктор решает проблему «не знаем типы заранее». Но у TCO эта проблема уже решена: данные есть в Master Fleet File.

**Следствие:** Делать полностью динамическую систему ради гипотетического нового типа в будущем — это over-engineering для Phase 1.

---

### Риск 2 — EAV убивает фильтрацию ⚠️ ВЫСОКИЙ

Если характеристики хранятся как «строки» в EAV-таблице, фильтрация по диапазонам невозможна или крайне дорогая.

**Пример проблемы:**
```
-- EAV-хранение
equipment_id | attribute_name | value
E001         | Грузоподъёмность | "5"     ← строка!
E002         | Грузоподъёмность | "10"
E003         | Грузоподъёмность | "2.5"

-- Запрос "найди с грузоподъёмностью > 4 тонн"
-- требует CAST, потеря индексов, полный скан
```

**Решение (если идти по этому пути):** обязательная типизация атрибута при создании: `string | number | boolean | enum`. Без этого фильтрация по диапазону (slider "от X до Y тонн") невозможна.

---

### Риск 3 — FO не должен быть архитектором данных ⚠️ СРЕДНИЙ

Роль FO в системе — управлять своим парком и отвечать на заявки. Создание типов техники и структуры характеристик — это задача **Администратора**, а не Fleet Owner-а.

**Проблемы, если FO создаёт типы:**
- Дублирование: два FO создадут «Грузоподъёмность» и «Максимальная грузоподъёмность» — это одно и то же
- Опечатки в именах характеристик → «Мощность кВт» и «Мощность, кВт» → не связаны
- Несовместимость единиц: один напишет «т», другой «кг» → невозможно сравнивать

---

### Риск 4 — Синхронизация с JDE и Master Fleet File ⚠️ СРЕДНИЙ

Данные о технике приходят из внешней системы (JDE E1, Master Fleet). Там структура фиксированная. Если в Booking Tool атрибуты динамические, нужен маппинг:

```
JDE: "alternator_output_kva" → Booking Tool: "Мощность генератора (кВА)"
```

Этот маппинг надо поддерживать вручную при обновлении справочника. Риск рассинхронизации.

---

### Риск 5 — Увеличение scope разработки ⚠️ СРЕДНИЙ

| Подход | Scope dev |
|--------|-----------|
| Фиксированная схема (текущая архитектура БД) | Baseline |
| Динамические атрибуты только для чтения/отображения | +20–30% |
| Полный конструктор (FO создаёт типы + атрибуты + фильтры) | +50–80% |

Для Phase 1 это существенно.

## Альтернативный подход: «полуконструктор» через Admin

Взять лучшее из идеи, убрать риски:

```
Кто управляет      Что делает
───────────────    ───────────────────────────────────
Admin              Создаёт/редактирует типы техники
Admin              Добавляет характеристики к типу (с типом данных: number/string/enum)
Admin              Ставит флаг «показывать в фильтрах»
─────────────────────────────────────────────────────
FO                 Добавляет единицу техники → выбирает тип → заполняет характеристики
FO                 Не создаёт новых типов и атрибутов
─────────────────────────────────────────────────────
Requestor          Видит динамические фильтры под тип техники (уже есть в матрице D-05)
```

Это реализует цель («не собирать требования по каждому типу»), но без рисков EAV без типизации и хаоса от FO-конструктора.

## Схема данных (если идти по полуконструктору)

```
equipment_types
  _id
  name: "Generator portable"
  hdv_hde_class: "Not SP motorized HDE"
  attributes: [
    { name: "Мощность генератора", unit: "кВА", type: "number", show_in_filter: true,  db_field: "alternator_output_kva" },
    { name: "Напряжение",          unit: "В",    type: "number", show_in_filter: true,  db_field: "system_voltage_v"      },
    { name: "Ёмкость батареи",     unit: "А·ч",  type: "number", show_in_filter: false, db_field: "battery_capacity_ah"  }
  ]

equipment
  _id
  equipment_type_id → equipment_types
  # Технические атрибуты — в отдельных типизированных полях (не EAV):
  alternator_output_kva: 100
  system_voltage_v: 380
  ...
```

**Ключевая точка:** атрибуты типа (metadata) — динамические. Значения конкретной единицы (data) — фиксированные поля в документе. Это даёт и гибкость, и производительность фильтрации.

## Итоговая оценка

| Критерий | Оценка |
|----------|--------|
| Концепция понятна и реализуема | ✅ Да |
| Решает реальную боль | ✅ Да — но для TCO боль частично уже решена (типы известны) |
| Готовность к Phase 1 | ⚠️ Полный конструктор — нет; упрощённый через Admin — да |
| Риск EAV без типизации | ❌ Высокий, если не продумать заранее |
| FO как архитектор данных | ❌ Не рекомендуется |
| Синхронизация с JDE/Master Fleet | ⚠️ Требует маппинга |

---

## Рекомендации

1. **Phase 1:** Зафиксировать типы техники и атрибуты из Master Fleet (уже сделано в матрице фильтров). Реализовать как Admin-настраиваемый справочник с типизированными атрибутами.

2. **Флаг «в фильтрах»** — реализовать обязательно. Это даёт гибкость без полного EAV.

3. **FO не создаёт типы.** Admin создаёт, FO использует. Так же как роли в других системах.

4. **Phase 2:** Если появится реальный запрос на добавление нового типа — тогда решать, нужен ли self-service конструктор для Admin-а.

5. **Уточнить у TCO (OQ-F9):** Планируют ли они добавлять новые типы техники в ближайший год? Если нет — конструктор вообще не нужен в Phase 1.
