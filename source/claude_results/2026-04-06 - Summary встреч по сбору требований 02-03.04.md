### 1. Что обсуждали

#### 1.1 AS-IS процесс бронирования

```
Operations планирует работы (например, замена клапана)
       ↓
Создаётся Work Order в JDE E1 (с кодировкой типа GDRV, JMLO, BHOE и др.)
       ↓
Планнер составляет план работ внутри Work Order
       ↓
Передаёт план графисту (через Power BI систему)
       ↓
Каждую пятницу графисты проводят собрание:
 - какие работы запланированы
 - какие виды работ
 - какая техника нужна
       ↓
Команды принимают "обязательства" → фиксируют в Excel на SharePoint
       ↓
Точное время выделения техники согласовывается день в день — по рации или устно
       ↓
Завершение брони — сообщают по рации (или выясняют сами, можно ли забрать технику)
```

**Специфика:** точное время не указывается — только дата + количество часов.

#### 1.2 Существующие инструменты и их недостатки

| Инструмент | Как используется | Проблема |
|-----------|-----------------|----------|
| JDE E1 | Work Orders, учёт внутренней техники | Нет интеграции с бронированием, нет видимости доступности |
| Power BI | Графисты формируют еженедельный план | Только чтение, нет взаимодействия с заявителями |
| Excel / SharePoint | Команды фиксируют обязательства | Разрозненные файлы, нет единого источника данных |
| Azure Synapse | Maintenance собирает файлы графистов | Агрегация, но не real-time |
| Power Apps (Equipment Tool) | Владельцы техники сами создают и утверждают заявки | Сложный доступ, не используется другими подразделениями |
| DCT | Оформление внешней техники (БП) | Нет данных о доступности конкретных единиц |

#### 1.3 Типы флота

| Тип | Описание | Текущая система |
|-----|----------|----------------|
| Internal (TCO-owned) | Собственная техника TCO | JDE E1 |
| Rented long-term (БП) | Аренда на год и более | DCT |
| Rented on-demand (БП) | Внешняя техника по запросу | DCT |

#### 1.4 Роли и согласование

- **Fleet Owner** — не один человек, а группа (2–3 человека на парк). Крупнейшие: Maintenance, Logistics.
- **Requestor** — любой сотрудник TCO. Для внешней техники нужна роль RWA-инициатора.
- **CC Owner** — подтверждает стоимость при бронировании внешней техники.

Цепочки согласования:
- Внутренний флот: только Fleet Owner
- Внешний флот: CC Owner → Fleet Owner (БП)

#### 1.5 Проблемные категории техники

**Не отслеживаются вообще:** генераторы, компрессоры, световые мачты, тепловые пушки, ман-лифты, вакуум-машины.

**Особая сложность — погрузчик:** в график закладывается только перевозка, работа не фиксируется. Компрессор может работать 4–5 дней — в системе не видно, что он занят.

### 1. Что обсуждали

#### 1.1 Ключевое решение: отказ от еженедельного планирования

**Зафиксировано:** TO-BE процесс — только фактическое бронирование по запросу. Еженедельные графики графистов **исключаются из нового процесса**.

- Графисты продолжат работать с Excel для других команд (вне области системы)
- В Booking Tool заявки создают сами реквесторы — в момент возникновения потребности
- Service Work Request (SWR) из JDE E1 — отдельный процесс, остаётся
- Цитата: *«Мы от графиков сейчас отходим, мы забываем про графики. Теперь у нас только фактическое бронирование»*

#### 1.2 Категории техники — финальное определение

Подтверждены **три категории** (ранее в BRD было неточно):

| Категория | Описание | Кто может использовать | Может ли Fleet Owner забрать? |
|-----------|----------|----------------------|-------------------------------|
| **Assigned** | Стационарная или специализированная техника (краны в зданиях, стационарные генераторы, авиационная техника) | Только назначенное подразделение | — |
| **Shared** | Передвижная техника, доступная для общего пользования | Любой Requestor | Нет — бронь до конца срока |
| **Shared with Conditions** | Передвижная техника, которая передаётся, но Fleet Owner может забрать в любой момент при наличии приоритетной потребности | Requestor с оговорками | **Да** — в любой момент |

**Важные уточнения:**
- **Assigned** — не отображается в поиске для Requestor-а вообще
- **Shared with Conditions** — отображается с визуальным маркером (цвет), чтобы Requestor понимал риск
- Почти вся стационарная техника → Assigned; вся передвижная → Shared или Shared with Conditions
- Конкретные единицы при работе над мастер-файлом флота помечались неверно — требуется ревизия (упоминание: «там где-то неправильно определены»)

#### 1.3 Приоритеты заявок (P1–P4)

Подтверждена система **четырёх приоритетов**:

| Приоритет | Смысл |
|-----------|-------|
| P1 | Наивысший — критические работы |
| P2 | Высокий |
| P3 | Средний |
| P4 | Низкий |

- Цель: Fleet Owner видит несколько входящих заявок на одну технику и принимает решение, кому отдать, исходя из приоритета
- Requestor при создании заявки сам выбирает приоритет + желательно краткое описание работ
- В перспективе: приоритет из JDE Work Order подтягивается автоматически

#### 1.4 Временны́е ограничения бронирования

| Параметр | Значение | Примечание |
|----------|---------|------------|
| Минимальный lead time | Нет жёсткого ограничения | Можно бронировать «минута в минуту» — для случаев, когда техника освободилась рядом |
| Максимальный горизонт планирования | **1 месяц** вперёд | Подтверждено заказчиком |
| Максимальная длительность одного бронирования | **1 неделя** | Подтверждено заказчиком |
| Разные периоды в одной заявке | **Да, должно быть возможно** | Пример: генератор на 24ч + компрессор на 6ч + погрузчик на 1ч — в одной заявке |

#### 1.5 Логистика доставки техники

Обнаружена важная тема, не отражённая в BRD:

- Расстояния в зоне ТШО: до 60 км (средняя до 30 км)
- Часть техники — **самоходная** (едет сама с водителем)
- Часть — **требует трала/прицепа** для перевозки (стационарные генераторы, тяжёлое оборудование)
- Бронирование считается начатым с момента **начала подготовки/мобилизации**, не с момента прибытия на объект

**Обсуждаемая логика (не финализирована):**

```
Requestor выбирает тип техники
       ↓
Система АВТОМАТИЧЕСКИ определяет:
  нужен ли трал/транспорт для доставки
       ↓
Если нужен трал → проверяет доступность трала
  Трал свободен → добавляет в заявку
  Трал занят → показывает ближайшую дату / предлагает трал от БП (с доп. стоимостью $)
```

- Requestor не должен думать о логистике доставки — это зона ответственности Fleet Owner / системы
- **Альтернативный вариант** (если автоматизация не реализуема): дополнительный шаг в процессе — Логистика назначает транспорт вручную при обработке заявки (аналог системы у drilling-партнёров)

#### 1.6 Тайм-аут ответа Fleet Owner

Если Fleet Owner не реагирует на заявку при наличии свободной техники:

1. Система отправляет **reminder-уведомление** (с копией руководителю на 2-й/3-й раз)
2. После истечения тайм-аута (обсуждалось: **24–48 часов**) заявка автоматически переходит во внешний флот
3. Параметр тайм-аута — **настраиваемый** (не hardcode)

#### 1.7 Одна заявка — несколько единиц техники разных Fleet Owner

Подтверждено:
- В одной заявке можно бронировать технику **нескольких внутренних Fleet Owner** одновременно (например, кран из Maintenance + генератор из другого парка)
- На практике такое редко, но функционально должно быть поддержано
- Если часть бронирований отклонена — подтверждённые продолжают работу, заявка не закрывается целиком

#### 1.8 UX: что видит Requestor

- Requestor видит **тип техники**, а не конкретный госномер/единицу
- Fleet Owner видит конкретные единицы и сам назначает
- Техника со статусом Assigned — **не отображается** в списке для Requestor
- Техника со статусом Shared with Conditions — отображается с **визуальным предупреждением**

#### 1.9 Интеграция с JDE E1 — уточнения

- JDE E1 **не выполняет бронирование** — это каталог работ с ресурсными потребностями
- При создании заявки Requestor указывает **номер JDE Work Order**
- Данные JDE доступны в DataLake → возможна интеграция, но нужно уточнить конкретные поля
- JDE будет вестись параллельно с Booking Tool (не заменяется)

#### 1.10 DataLake и трекеры — текущие блокеры

- WIALON-данные стоят на блоке (разрабатывается новый поток данных через data architect)
- eDrive данные пока не тянутся → утилизация в дашборде неполная (~35–45%, приближённо)
- Стратегия: оснастить **весь флот** датчиками для 100% видимости
- Геолокация Work Order из JDE — технически возможна через DataLake

#### 1.11 Чат-заметки: принцип проектирования

- Максимальный срок бронирования — **настраиваемый параметр через панель Администратора**, не hardcode
- Общий принцип: «как можно меньше hardcoded solutions — иначе куча новых IT MOC в будущем»

## Ключевые инсайты для проектирования

1. **Отказ от еженедельного планирования** — принципиальное TO-BE решение: система работает только в режиме on-demand. Графисты остаются вне системы.

2. **Три категории техники** (не две, как в BRD): Assigned / Shared / Shared with Conditions — с разной видимостью в UI и разными правилами бронирования.

3. **Логистика доставки — незакрытая тема**: система потенциально должна автоматически определять необходимость трала. Это новый функциональный блок, не описанный в BRD.

4. **Тайм-аут Fleet Owner с эскалацией** — механизм предотвращения зависших заявок: reminder → эскалация на руководителя → авто-переход во внешний флот.

5. **Временны́е границы**: горизонт бронирования — 1 месяц; длительность брони — 1 неделя; минимальный lead time — не ограничен (можно «минута в минуту» для экстренных случаев).

6. **Hardcode = технический долг**: тайм-аут, максимальный срок, приоритеты — всё через Admin panel.

7. **JDE Work Order номер** обязателен при создании заявки — важно для трассируемости работ.

8. **Requestor видит тип, Fleet Owner — конкретную единицу**: разграничение в UX важно для проектирования интерфейсов.

9. **Данные трекеров** (WIALON, eDrive) — технические блокеры со стороны TCO. На момент встречи утилизация в дашборде неполная (~35–45%).
