## Принятые решения

### По итогам встречи (зафиксировано в резюме):
- **Приоритет внутренней техники:** система не может принудительно обеспечить при текущей модели выбора конкретной техники; остаётся бизнес-правилом
- **Несколько техник в форме:** реквестер заполняет одну форму, система разбивает на атомарные заявки; группировка через Work Order
- **Закрытие заявки:** только кнопкой, не автоматически по времени
- **Мобилизация:** добавить кнопку «Мобилизация началась» на стороне флит-оунера
- **Транспортировка нетягловой техники:** трёхшаговый флоу (FO добавляет транспорт → роль «транспортировка» подтверждает → FO даёт финальное ок); создать отдельную роль в системе; две ответственные группы: Heavy Ops (Ерлан) и команда Азбека
- **Буфер между бронями:** не требуется

### Рекомендация BA по архитектуре (обсуждение после встречи):
- **Гибридная модель:** лёгкая заявка (Request) + атомарные брони (Booking)
- Заявка существует в БД, но с минимальным ЖЦ: хранит реквестера, WO, приоритет; статус — вычисляемый (агрегат броней), только read-only
- Бронь — основная операционная единица с полным ЖЦ, своим флит-оунером, своей цепочкой согласования
- Кейс «неделимого пакета» (техника неделима) — в Фазе 1 не реализовывать жёсткую зависимость; достаточно уведомления реквестеру при отклонении любой брони
