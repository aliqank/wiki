# Контекст сессии — 2026-04-13

## Что делали

- Обсуждали архитектурный вопрос: нужна ли отдельная сущность `Booking`, если она дублирует данные `RequestItem`
- Разобрали флоу заявок: Requestor выбирает конкретную технику при создании; FO может поменять технику перед приёмом; нужна проверка свободности
- Сформировали аргументы за и против каждого варианта
- Обновили блок "Структура сущностей" в файле материалов для встречи с командой разработки: добавили два варианта с диаграммами, коллекциями, статус-машинами, плюсами и минусами

## Принятые решения

- **Решение не принято** — намеренно: вопрос выносится на встречу с командой разработки, они выбирают вариант
- Сформулированы два варианта:
  - **Вариант A** — `RequestItem` + отдельный `Booking` (1:1); `equipmentId` на Booking может отличаться от RequestItem (FO-замена)
  - **Вариант B** — только `RequestItem` без `Booking`; два поля: `requestedEquipmentId` + `assignedEquipmentId`; замена видна через audit_log
- Ключевой аргумент за Вариант B: раз Requestor выбирает конкретную технику сразу, нет фазы "тип без единицы" → Booking не добавляет семантики
- Ключевой аргумент за Вариант A: чёткое разделение "запрос" vs "факт", история замены структурно выражена
