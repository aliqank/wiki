# ТЗ на макет: Fleet Owner — список броней и агрегированные заявки

**Дата:** 2026-05-19
**Для кого:** Дизайнер (Figma-макет)
**Подготовил:** Тельман Нуржанов SA

---

## Назначение документа

Документ описывает UX-структуру и состав элементов для экрана Fleet Owner, в котором пользователь может переключаться между двумя представлениями одного и того же потока согласования:
- список отдельных броней;
- список агрегированных заявок с вложенными бронями.

**Что описывает:** состав экранов, фильтры, поведение переключателя view, поля таблиц/карточек, состояния интерфейса, взаимодействия пользователя.

**Что НЕ описывает:** визуальный стиль, точные API-контракты, правила авторизации на уровне backend, финальную цветовую систему статусов.

---

## 1. Общая концепция

### 1.1 Назначение экрана

Fleet Owner должен иметь возможность работать в двух режимах:
- **View 1: `Bookings`** — операционная очередь, где одна строка = одна бронь;
- **View 2: `Requests`** — агрегированный список заявок, где одна строка / карточка = одна заявка, внутри которой отображаются связанные брони.

Обе view должны быть доступны в одном функциональном разделе через явный переключатель.

### 1.2 Общий layout

**Хедер страницы:**
- Заголовок: `Approvals`
- Подзаголовок: краткое пояснение, что экран предназначен для обработки входящих заявок / броней Fleet Owner

**Переключатель view:**
- Сегментированный switch / tabs:
  - `Bookings`
  - `Requests`
- Активная view визуально выделена
- Переключение не должно выглядеть как навигация в другой модуль; это два представления одной области

**Общие зоны экрана:**
- Верхняя зона: заголовок + switch view
- Панель фильтров
- Таблица / список результатов
- Пагинация

### 1.3 Общие принципы поведения

- Обе view используют один и тот же экранный контейнер
- При переключении между view фильтры могут сохраняться, если это улучшает UX
- Если набор фильтров у view отличается, дизайнер должен предусмотреть адаптацию панели фильтров без ощущения «ломающегося» интерфейса
- Desktop-first: экран ориентирован на работу в таблицах, массовый просмотр и операционную обработку

## 2. View FO-01: Bookings

**Рабочее название:** `My Bookings`

**Назначение:** дать Fleet Owner быстрый операционный список входящих броней для обработки.

### 2.1 Логика view

- Одна строка = одна бронь
- Каждая строка должна содержать и request-level контекст, и booking-level данные
- View предназначена для быстрого просмотра, сортировки, SLA-ориентированной обработки и перехода в detail action flow

### 2.2 Панель фильтров

Минимальный набор фильтров для view `Bookings`:
- Тип заявки
- Статус заявки / брони
- Период заявки
- Поиск по Work Order

Дополнительно дизайнер должен предусмотреть место под потенциальные фильтры второй итерации:
- Тип техники
- Подвижность техники
- ТШО номер / ГРНЗ

**Поиск по Work Order:**
- один input
- поиск выполняется по обоим WO-полям системы
- partial search, без требования точного совпадения

**Период заявки:**
- диапазон дат `from - to`
- должен выглядеть как единый контрол с двумя значениями

### 2.3 Таблица результатов

Рекомендуемый состав колонок:

| Колонка | Смысл |
|---|---|
| Номер заявки | Request number |
| Дата создания заявки | Когда создан request |
| Requestor | Кто создал заявку |
| Work Order | Номер WO |
| Приоритет | Request priority |
| Статус заявки | Общий статус request |
| Дата создания брони | Когда создан booking |
| Подвижность техники | Mobility type |
| Тип техники | Equipment type |
| Марка / модель | Brand + model |
| ТШО номер | Equipment TCO ID |
| ГРНЗ | State number |
| Даты брони | Start / End |
| Статус брони | Booking status |
| Таймер | Время с момента поступления в очередь FO |

### 2.4 Поведение строки

- Клик по строке открывает detail / action screen конкретной брони
- В строке допустимы status badges
- Приоритет должен быть визуально заметен, но не доминировать над статусом
- Таймер должен быть отдельным визуальным элементом, а не просто текстовой датой

### 2.5 Таймер

Таймер считается **с момента поступления конкретной брони в очередь Fleet Owner**.

Для дизайна предусмотреть:
- компактное отображение таймера в строке;
- состояние normal / warning / critical;
- место под tooltip с точной датой/временем поступления.

Пороговые значения цветов могут быть уточнены позже; дизайнеру нужно заложить сам паттерн отображения.

### 2.6 Состояния view `Bookings`

- Loading: skeleton / shimmer таблицы
- Empty: нет доступных броней по текущим фильтрам
- Error: не удалось загрузить список
- Long list: sticky header таблицы

## 3. View FO-02: Requests

**Рабочее название:** `Requests`

**Назначение:** показать Fleet Owner агрегированную картину заявки целиком, с вложенными бронями.

### 3.1 Логика view

- Одна строка / карточка = одна заявка
- Внутри заявки отображаются связанные booking-ы
- View нужна для понимания контекста, состава заявки и связанных единиц техники

### 3.2 Панель фильтров

Для view `Requests` обязательны:
- Тип заявки
- Статус заявки
- Период заявки
- Поиск по Work Order

Поиск и период — по тем же принципам, что и в `Bookings` view.

### 3.3 Представление результата

Рекомендуемый формат:
- таблица заявок с expandable rows
или
- список карточек заявок с раскрывающимся блоком `Bookings`

Дизайнер может выбрать более сильный паттерн, но важно сохранить читаемость при большом количестве вложенных броней.

### 3.4 Поля верхнего уровня заявки

| Поле | Смысл |
|---|---|
| Номер заявки | Request number |
| Дата создания | Request created at |
| Requestor | Автор заявки |
| Work Order | WO |
| Приоритет | Request priority |
| Статус | Aggregated request status |

Дополнительно желательно предусмотреть место под summary indicators:
- количество броней в заявке;
- количество броней, требующих действия FO;
- признак mixed-status заявки.

### 3.5 Вложенный список броней

Для каждой заявки внутри раскрытия должны отображаться booking-поля:

| Поле | Смысл |
|---|---|
| Дата создания брони | Booking created at |
| Подвижность техники | Mobility type |
| Тип техники | Equipment type |
| Марка / модель | Brand + model |
| ТШО номер | Equipment TCO ID |
| ГРНЗ | State number |
| Даты брони | Start / End |
| Статус | Booking status |
| Таймер | Время с момента поступления брони в очередь FO |

### 3.6 Поведение заявки

- В collapsed state пользователь видит только request-level summary
- В expanded state видит все связанные брони, доступные ему как Fleet Owner
- Expand / collapse должен быть заметным и быстрым
- Если у заявки только одна бронь, интерфейс всё равно должен выглядеть консистентно

### 3.7 Состояния view `Requests`

- Loading: skeleton карточек / строк заявок
- Empty: нет заявок по текущим фильтрам
- Error: не удалось загрузить список
- Expanded content overflow: designer должен предусмотреть читаемость при 5+ вложенных booking-ах

## 4. Общие UX-требования

### 4.1 Статусы

Нужно визуально различать:
- статус заявки;
- статус конкретной брони.

Нельзя использовать один и тот же визуальный паттерн так, чтобы request status и booking status путались между собой.

### 4.2 Приоритет

Приоритет заявки должен быть заметен:
- badge / tag / accent marker
- но не должен конкурировать со статусом и таймером

### 4.3 Requestor

В результатах желательно отображать:
- полное имя requestor-а;
- при необходимости secondary text для email или подразделения в будущих итерациях.

### 4.4 Work Order

Work Order — одно из ключевых полей поиска и ориентации пользователя.

Для дизайна предусмотреть:
- достаточную ширину колонки / области;
- перенос / tooltip при длинных значениях;
- заметность search match.

### 4.5 Подвижность техники

Поле должно быть выделено как отдельный атрибут техники.

Для дизайна допустимы варианты:
- текст;
- иконка + текст;
- badge.

Главное: различие типов мобильности должно считываться быстро.

## 5. Состояния интерфейса

Для обеих view дизайнер должен показать:
- default state;
- loading state;
- empty state;
- error state;
- filtered state с активными фильтрами;
- expanded state для request-centric view.

Ожидаемый набор макетов:

## 7. Открытые допущения для дизайнера

На момент подготовки ТЗ допустимы следующие проектные допущения:
- view `Bookings` и `Requests` находятся в одном разделе и переключаются без отдельного меню;
- request-centric view показывает только те booking-и, которые относятся к зоне ответственности текущего Fleet Owner;
- aggregated request status будет вычисляться backend-ом и передаваться в UI как готовое значение;
- таймер отображает возраст брони в очереди FO, а не возраст всей заявки.

Если при проектировании дизайнер увидит, что табличное представление request-centric view сильно перегружает экран, допускается переход к карточному представлению заявок при сохранении всех обязательных данных.

## 9. Открытые вопросы для BA / SA

Ниже перечислены вопросы, которые пока не должны блокировать подготовку макета, но требуют дальнейшего уточнения в аналитике и API.

| ID | Вопрос | Почему важен для дизайна |
|---|---|---|
| OQ-FO-01 | Что именно считается **статусом заявки** в view `Requests`: статус `BookingRequest` или агрегированное значение, вычисленное по вложенным booking-ам? | От этого зависит структура badge-ов и логика отображения mixed-state заявки |
| OQ-FO-02 | Нужно ли в request-centric view показывать **все booking-и заявки** или только те, которые относятся к флотам текущего Fleet Owner? | Влияет на состав раскрытия заявки и риск перегрузки / раскрытия лишних данных |
| OQ-FO-03 | Какой именно **набор статусов** должен быть доступен в фильтре для view `Bookings` и для view `Requests`? | Нужно спроектировать фильтр статусов и состояния badge-ов |
| OQ-FO-04 | Как именно рассчитывается **таймер**: от момента `BookingStatuses.Submitted`, от момента создания booking или от другого SLA timestamp? | Влияет на подписи, tooltip и доверие пользователя к таймеру |
| OQ-FO-05 | Какие пороги используются для состояний таймера `normal / warning / critical`? | Нужны для финальной цветовой логики и приоритизации внимания |
| OQ-FO-06 | Что означает поле **«подвижность техники»** в терминах справочника: точный enum, набор значений, нужны ли иконки? | Влияет на форму отображения поля в таблице и в раскрытии заявки |
| OQ-FO-07 | Поиск по Work Order выполняется по **каким именно двум полям**? Только `workOrderNumber` и linked JDE reference, или есть второе пользовательское поле? | Влияет на microcopy search input и ожидаемое поведение пользователя |
| OQ-FO-08 | Нужно ли в `Bookings` view поддерживать **массовые действия** (например, multi-select и batch confirm/decline) или обработка строго построчная? | Влияет на наличие чекбоксов, toolbar действий и плотность таблицы |
| OQ-FO-09 | Нужен ли в `Requests` view явный индикатор **«есть брони, требующие моего действия»** и как он считается? | Влияет на summary indicators верхнего уровня заявки |
| OQ-FO-10 | Нужно ли сохранять один и тот же набор фильтров при переключении между `Bookings` и `Requests`, или у каждой view должно быть собственное состояние фильтров? | Влияет на UX переключателя и поведение панели фильтров |

Если ответы на эти вопросы будут получены после первого макета, дизайнер может выпускать v1 макета с текущими допущениями, а затем подготовить точечную v2-итерацию без пересборки всей структуры экрана.
