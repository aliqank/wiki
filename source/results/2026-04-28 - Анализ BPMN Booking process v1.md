# Анализ BPMN: Booking process v1
*Дата: 2026-04-28 | Файл: Документация в процессе работы с требованиями/2026-04-28/Booking process v1.bpmn*

---

## Краткое резюме

Диаграмма описывает процесс бронирования техники через коллаборацию трёх пулов: Requestor, System, и (безымянный) Fleet Owner. Основные проблемы — разрывы в sequence flows, неподключённые элементы, опечатки и смешанные конвенции именования.

---

## 1. Критические структурные проблемы (обрывы процесса)

### 1.1. Безымянный третий участник
`Participant_1am2fdj` — пул Fleet Owner — **не имеет атрибута `name`**. На диаграмме это отображается как пустой заголовок пула.

**Исправление:** добавить `name="Fleet Owner"`.

---

### 1.2. Задачи без исходящих sequence flows (тупики в Requestor)

| ID | Название | Проблема |
|----|----------|----------|
| `Activity_0jtx1qf` | Нажать "Добавить технику" | Нет `<bpmn:outgoing>` — процесс Requestor обрывается после нажатия кнопки |
| `Activity_0c4196b` | Выбрать и добавить технику к заявке | Нет `<bpmn:outgoing>` — после выбора техники Requestor завис |
| `Activity_1mr82or` | Отправить заявку | Нет `<bpmn:outgoing>` — после отправки Requestor ничего не делает |

В реальности Requestor должен после каждого из этих действий ждать ответа системы. Необходимо добавить либо intermediate message catch event (ожидание ответа), либо явный sequence flow к следующей задаче.

---

### 1.3. Задачи без входящих sequence flows (висячие острова)

| ID | Название | Проблема |
|----|----------|----------|
| `Activity_0pc73xf` | Изменить параметры поиска | Входящий только message flow — в пуле Requestor нет sequence flow к этой задаче |
| `Activity_102e4yk` | Начать работу | Аналогично — только message flow, нет sequence flow внутри пула |
| `Activity_0ovkmmd` | Продолжить работу с заявкой (System) | Только message flow от `Activity_0p8va94`, нет sequence flow |

---

### 1.4. Полностью отвязанные элементы

- **`Event_1j46r8n`** ("Техника завершила работу") — intermediate conditional catch event **без единого входящего или исходящего** sequence/message flow. Элемент висит в воздухе.
- **`Event_053m7hv`** ("Техника прибыла на место") — boundary event на `Activity_102e4yk`, но **нет исходящего потока**. Граничное событие без последствий.

---

### 1.5. Отсутствуют End Events в двух пулах

- Пул **Requestor**: нет явного конечного события. Процесс завершается неявно после `Activity_0ca6vx5` ("Завершить бронь").
- Пул **System**: нет ни одного конечного события.

Рекомендуется добавить End Events для ясности и корректной интерпретации движком Camunda.

---

## 2. Логические проблемы процесса

### 2.1. Четыре задачи с одинаковым именем "Продолжить работу с заявкой"

| ID | Пул |
|----|-----|
| `Activity_0qnyih7` | Requestor |
| `Activity_0308nki` | Fleet Owner |
| `Activity_1wl1gz8` | Fleet Owner |
| `Activity_0ovkmmd` | System |

Это затрудняет чтение схемы. Рекомендуется переименовать каждую задачу, отражая конкретное действие (например: "Проверить список техники", "Обновить заявку после замены", "Перейти к подтверждению брони").

---

### 2.2. Недостижимый цикл при недоступности техники

Когда система показывает "Техника недоступна" (`Activity_0nmsx2t`), message flow ведёт к `Activity_0pc73xf` ("Изменить параметры поиска"). Но:
- У пользователя нет явного выбора: **повторить поиск** или **отказаться от техники**.
- Нет выхода из цикла — можно зациклиться бесконечно.

**Рекомендация:** добавить exclusive gateway после уведомления о недоступности: «Изменить параметры?» → Да / Нет (выйти из модального окна без добавления техники).

---

### 2.3. Неоднозначность "Варианты изменения" (`Activity_1xzp726`)

Задача Fleet Owner при невозможности предоставить технику. Аннотация поясняет, что нужно рассмотреть замену техники и/или периода — но это уже задача с принятием решения. По факту здесь должен быть **gateway**, а не task, или как минимум task должна вести к двум explicit гейтвеям (что и сделано далее). Текущее название не отражает конкретного действия — лучше: "Рассмотреть варианты изменения брони".

---

### 2.4. Нет уведомления Requestor об отказе Fleet Owner

Когда Fleet Owner отклоняет бронь (`Activity_1gmt9vn`, `Activity_179183j`), оба пути ведут в End Event — но **Requestor никогда не узнаёт об отказе**. Нет message flow к System или Requestor с уведомлением.

---

### 2.5. Подпроцесс оформлен как обычная задача

`Activity_1vn39aq` ("Под-процесс по назначению транспорта...") явно должен быть **Collapsed Sub-Process** (`callActivity` или `subProcess` в BPMN), а не обычным task. Сейчас это не моделируется как подпроцесс и не может быть выполнено движком.

---

### 2.6. Петля "Запросить транспорт у коллег" без условия выхода

`Activity_1anyzin` → ответ коллег → `Activity_1h0lvm6` → Gateway → Да (снова `Activity_1anyzin`) или Нет (отклонить). Но нет ограничения количества попыток и нет таймаута — потенциально бесконечный цикл.

---

## 3. Технические проблемы (Camunda)

### 3.1. Пустые условия в conditional events

Все `conditionalEventDefinition` содержат пустое выражение:
```xml
<bpmn:condition xsi:type="bpmn:tFormalExpression" />
```
Для исполняемого процесса необходимо заполнить выражения (например, JUEL или Groovy). Без этого Camunda не сможет определить, когда срабатывает событие.

Затронутые элементы: `Event_053m7hv`, `Event_1j46r8n`, `Event_0qr57xu`.

---

### 3.2. Пустой Timer в intermediate event

`Event_1a2wvpt` ("Техника выполняет работу") — таймер без определения:
```xml
<bpmn:timerEventDefinition id="TimerEventDefinition_0t393ci" />
```
Нет `timeDuration`, `timeDate` или `timeCycle`. Процесс не выполнится.

---

### 3.3. Задачи в пуле Requestor не помечены как UserTask

Все активности Requestor объявлены как `<bpmn:task>` (abstract task). Для Camunda 7 действия пользователя должны быть `<bpmn:userTask>` с атрибутами `assignee`/`candidateGroups`. Иначе они будут выполнены автоматически (без human interaction).

---

### 3.4. Process_0md5m48 помечен isExecutable="true" при неполной модели

Requestor pool помечен как исполняемый, но в нём есть разрывы в sequence flows (п. 1.2–1.3). Camunda выдаст ошибку валидации при деплое.

## 4. Опечатки и именование

| ID | Текущее | Должно быть |
|----|---------|-------------|
| `Activity_1gmt9vn` | "Отколнить бронь" | "Отклонить бронь" |
| `Activity_1vn39aq` | "...у сновного fleetOwner" | "...у основного Fleet Owner" |
| `Activity_179183j` | "отклонить бронь" (строчная) | "Отклонить бронь" (заглавная, единообразно) |

### Непоследовательная капитализация меток на шлюзах

Метки потоков из шлюзов используют "Да"/"да" и "Нет"/"нет" смешанно:
- `Flow_11hyudr`: "да" (строчная)
- `Flow_0dhzkrm`: "нет" (строчная)
- остальные: "Да"/"Нет" (заглавная)

Рекомендуется везде использовать заглавную букву.
