## 1. Приоритет внутренней техники перед внешней

**Обсуждение:** Ранее договорились, что реквестер сам выбирает конкретную единицу техники (не тип). Это создаёт противоречие с требованием «приоритет внутренней техники ТШО перед external on-demand»: система не может технически обеспечить этот приоритет, если пользователь может напрямую перейти в каталог.

**Решение/статус:**
- Приоритет остаётся бизнес-правилом, но не может быть жёстко принудит в системе при текущей модели выбора техники.
- Опция: скрывать внешний каталог, если по данному типу есть свободная внутренняя техника — обсудить на уровне UX.
- Если флит-оунер не подтверждает в отведённое время — реквестер перенаправляется на внешний каталог.
- Long-term rented техника "приравнивается" к own (процесс бронирования как у внутренней техники).

**Открытый вопрос:** Нужно ли реализовать скрытие каталога при наличии свободной внутренней техники?

## 2. Несколько единиц техники в одной заявке

**Обсуждение:** Требование — возможность добавить несколько единиц техники в рамках одной заявки. Проблема: у каждой единицы может быть разный статус, разные fleet owner'ы, разное время завершения — определение «статуса заявки» становится сложным.

**Решение:**
- Реквестер формирует **одну форму** (одно окно) с несколькими единицами техники.
- При отправке система **автоматически разбивает** форму на **атомарные отдельные заявки** — по одной на каждую единицу техники.
- Все заявки из одной формы можно найти через **фильтр по Work Order** (поле в заявке).
- Каждая заявка живёт и закрывается независимо.

**Кейс «неделимого пакета»:** Бывают ситуации, когда без одной техники нет смысла заказывать другую (например, погрузчик + компрессор для одной работы). Решение по этому кейсу **будет продумано дополнительно** (возможна логика связанных заявок).

## 3. Статус и жизненный цикл заявки

**Уточнения:**
- Закрытие заявки — **по кнопке** (вручную инициатором или флит-оунером), **не автоматически по времени**. Автозакрытие создаёт конфликты (техника может работать дольше запланированного).
- Реквестер при закрытии указывает **фактическое время начала и окончания работ** — это нужно для аналитики утилизации. Разница между временем брони и фактическим временем работ = время мобилизации.
- Флит-оунер может редактировать время **до подтверждения**. Изменения после подтверждения — обсуждается (требование BRD: *update booking period before confirmation*).
- Флит-оунер может предлагать **перенос** заявки с комментарием (например, погодные условия).

## 4. Мобилизация: старт фиксации

**Обсуждение:** Бронирование стартует с момента начала мобилизации (не с момента прибытия техники на объект). Как система фиксирует старт мобилизации?

**Решение:** Добавить кнопку **«Мобилизация началась»** на стороне флит-оунера. Нажатие = старт фактической мобилизации в системе.

## 5. Транспортировка нетягловой техники — трёхшаговый процесс

**Контекст:** Часть техники не самоходная (не может добраться своим ходом). Кто организует доставку?

**Решение:**
- Флит-оунер **сам добавляет** технику для перевозки в заявку (ручной режим, Фаза 1).
- Транспортировкой занимаются **две группы:** Heavy Ops (команда Ерлана) и команда Азбека. Других групп с соответствующей техникой нет.
- Для роли «ответственный за транспортировку/мобилизацию» создаётся **отдельная роль в системе** — к ней будут привязаны соответствующие пользователи.
- По типу техники (колонка *propelled / not motorized* в Master Fleet File) система сможет определять, нужна ли транспортировка.

**Трёхшаговый флоу для техники с транспортировкой:**
1. Реквестер создаёт заявку → приходит флит-оунеру.
2. Флит-оунер добавляет технику для доставки → запрос уходит роли «транспортировка» (Heavy Ops / Азбек).
3. Роль «транспортировка» подтверждает готовность доставить.
4. Флит-оунер получает подтверждение и окончательно утверждает заявку → заявка уходит в работу.

> Флит-оунер подтверждает **только при условии**, что доставка подтверждена.

**Погодный форс-мажор:** Если в день доставки погода изменилась (ветер, снег, крановые работы запрещены) — ответственный за транспортировку **связывается с инициатором по телефону**, инициатор отменяет или переносит заявку в системе.

## 6. Буфер времени между бронями

**Вопрос:** Нужно ли минимальное время между окончанием одной брони и началом следующей?

**Решение:** Нет фиксированного обязательного буфера. Вопрос доставки решается на уровне логики мобилизации и ответственности флит-оунера, а не блокировкой в системе.

---

## 7. Прочие уточнения

- В заявке одна Work Order (нельзя несколько WO на одну заявку).
- Реквестер **не может** добавить технику разных категорий у разных флит-оунеров на разные WO в одну форму — это разные заявки.
- История всех бронирований — **по запросу** (аудит), не ежедневные/еженедельные отчёты.
