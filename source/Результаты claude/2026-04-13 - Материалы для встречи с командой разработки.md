## 1. Контекст

**Клиент:** TCO (Tengizchevroil) — крупнейший нефтедобывающий оператор в Казахстане.

**Домен:** Управление бронированием тяжёлой техники и оборудования.

- **HDV** — Heavy Duty Vehicles (самоходная техника: самосвалы, погрузчики, краны, бульдозеры)
- **HDE** — Heavy Duty Equipment (оборудование: генераторы, компрессоры, ман-лифты, осветительные мачты)

**Масштаб парка:** ~786 единиц техники в управлении Логистики TCO.  
**Пользователи системы:** ~200 сотрудников TCO.

**Ключевые боли заказчика:**

| Боль | Описание |
|------|----------|
| Нет единой системы учёта | Excel, устные договорённости, несколько баз данных |
| Конфликты бронирований | Одну технику могут «закрепить» за двумя командами на одну дату |
| Нет видимости по утилизации | Генераторы, компрессоры, ман-лифты — неизвестно, используются ли |
| Нет прозрачности затрат | Сколько тратим на аренду внешней техники — неизвестно |
| Ручные процессы | Бронирование через JDE, Excel, рации и звонки |

## 2. AS-IS процесс

### Как сейчас устроено бронирование

```
Requestor (сотрудник TCO)
  ↓
  Создаёт заявку в JDE E1 или звонит Fleet Owner напрямую
  ↓
Fleet Owner (владелец парка техники)
  ↓
  Подтверждает устно / в Excel-графике / в JDE
  ↓
Еженедельный графист
  ↓
  Сводит всё в Excel → публикует в SharePoint → Power BI
```

**Проблемы:**
- Нет предотвращения конфликтов — два диспетчера могут одновременно забронировать одну единицу
- Завершение брони сообщается по рации или не сообщается вообще
- Данные от внешних подрядчиков (БП) отсутствуют полностью
- Существующий «Equipment tool» в Power Apps не используется — слишком сложный интерфейс

## 4. Роли пользователей

| Роль | Кто | Что делает в системе |
|------|-----|----------------------|
| **Requestor** | Любой сотрудник TCO | Ищет технику, создаёт заявки, отслеживает статус, закрывает бронь, вводит фактическое время |
| **Fleet Owner (FO)** | Владелец/менеджер парка | Управляет техникой, подтверждает/отклоняет, редактирует период брони, нажимает «Мобилизация началась», добавляет транспорт для Unwheeled |
| **Transportation Responsible** | Команда Heavy Ops / обслуживания | Получает уведомление о транспортировке Unwheeled техники, подтверждает/отклоняет готовность к перемещению |
| **Admin** | Логистика TCO | Настройки системы, управление парками и флотами, авторизация доступа к Assigned-технике, управление шаблонами |
| ~~**CC Owner**~~ | ~~Владелец центра затрат~~ | ❌ **Obsolete** — бронирование BP-техники происходит в DCT, а не в этом инструменте |

### Ключевые нюансы ролей

- **FO может делегировать** полномочия любому сотруднику TCO на указанный период (start + end date); по истечении — автоматически отзывается (FR-NEW-02)
- **Один FO может управлять несколькими флотами** (быть в нескольких AAD группах) (FR-019)
- **Fleet имеет уникальное имя** (Heavy Ops, Logistics, Maintenance, Production…); техника привязана к конкретному сотруднику, не к отделу — при смене FO Admin переназначает вручную
- **Assigned-техника**: видна всем, но бронировать могут только пользователи, авторизованные Admin + обязательный Justification (FR-NEW-08)
- **Long-term rented техника** бронируется как собственная TCO — CC Owner не нужен (подтверждено 10.04)
- **Service Work Processor** — ⚠️ роль не определена (OQ-NEW-C); временно исключена из активных требований

## 6. Ключевые требования

### 6.1 Классификация техники (3 измерения)

**По владению:**

| Тип | Описание | Бронирование в системе |
|-----|----------|------------------------|
| **TCO Owned** | Собственная техника ТШО | ✅ Полное |
| **Long-term rented** | Долгосрочная аренда у БП; управляется внутренней командой TCO | ✅ Как собственная (без доп. авторизации) |
| **On-demand rented (BP Showcase)** | Аренда по запросу у БП | ❌ Реализация = только витрина; само бронирование — в DCT |

**По статусу использования:**

| Статус | Описание |
|--------|----------|
| **Shared without Conditions** | Доступна всем без ограничений |
| **Shared with Conditions** | Доступна, но FO может перераспределить под более приоритетные задачи; отображается с цветовым маркером |
| **Assigned** | Закреплена за подразделением; **видна всем**, но бронируется только авторизованными Admin + обязательный Justification |

**По мобильности:**

| Тип | Описание | Особенность |
|-----|----------|-------------|
| **Self-propelled (HDV/HDE)** | Едет сама | Стандартный флоу |
| **Not self-propelled (Unwheeled)** | Двигатель есть, но нужна доставка | Трёхшаговый флоу с Transportation Responsible |
| **Non-motorized (Unwheeled)** | Без двигателя | Трёхшаговый флоу с Transportation Responsible |
| **Stationary HDE** | Стационарная | Не отображается в поиске Requestor-а |

> **Мобильность не отображается в UI Requestor-а** — Requestor видит плоский список типов техники (погрузчики, компрессоры, краны и т.д.).

### 6.2 Утилизация (новое в BRD v3)

**Utilization** — ежедневная эффективность использования техники.

- Отслеживается по **пробегу** (колёсная техника) или **моточасам** (прочая)
- **Каждый FO самостоятельно** устанавливает порог 100% утилизации для каждого типа техники своего парка (например: 2 ч работы в сутки = 100%)
- **Maximum Utilization Capacity per Shift** — максимально возможная утилизация за рабочую смену (отправная точка для расчётов)
- Расчёт: по дням, месяцам или любому выбранному периоду
- Источник данных: IVMS + Vega трекеры → DataLake → система

### 6.3 Жизненный цикл бронирования

#### Стандартный флоу (Self-propelled техника)

```
Requestor          Fleet Owner            System
    │                   │                    │
    │─ Создаёт заявку ──►│◄── Уведомление ────│
    │  (техника, период, │                    │
    │   WO#, P1-P4)      │    [24ч → reminder]│
    │                    │    [48ч → эскалация│
    │                    │     + кнопка       │
    │                    │     "Перейти в BP"]│
    │◄── Уведомление ────│─ Подтверждает ─────►│ (или отклоняет с причиной)
    │   (или отклонение) │                    │
    │                    │─ «Мобилизация      │
    │                    │   началась» ────────►│ (фиксирует start)
    │                    │                    │
    │─ Close (кнопка) ───►│                    │ ← Requestor ИЛИ FO
    │  Вводит фактич.    │                    │
    │  start/end time    │                    │
```

#### Флоу для Unwheeled (трёхшаговый, FR-NEW-29)

```
Requestor       Fleet Owner     Transportation Responsible
    │                │                    │
    │─ Заявка ────►  │                    │
    │                │─ Добавляет транспорт│
    │                │  для перемещения ──►│◄── Уведомление
    │                │                    │─ Подтверждает /
    │                │◄── Уведомление ────│   отклоняет
    │                │
    │                │ FO может подтвердить ТОЛЬКО
    │                │ если транспортировка подтверждена
    │◄── Статус ─────│
```

#### Статусы заявки (Request — агрегированный):
```
draft → submitted → partially_confirmed → fully_confirmed → in_progress → completed
                                        ↘ cancelled
```

#### Статусы брони (Booking):
```
submitted → confirmed → in_progress → completed
          → declined                → terminated (ранний выход)
          → revoked (отозвана Requestor-ом)
```

> **⚠️ CONFLICT-02 (открытый):** BRD FR-070/071/075 предполагает **автоматический** переход статусов по времени (datetime >= booking start/end). Решение встречи 09.04 (R-75): **закрытие только вручную** по кнопке. Нужен явный sign-off от TCO.  
> *Сейчас принято: ручное закрытие (FR-NEW-32) — автопереход не применяется.*

### 6.4 Ключевые правила работы системы

| Правило | Источник |
|---------|---------|
| Заявка = одна форма → система автоматически разбивает на атомарные брони (по одной на единицу техники) | FR-NEW-15 |
| При нескольких позициях — частичное подтверждение; каждая позиция идёт независимо | FR-NEW-16 |
| Отказ FO не закрывает заявку — Requestor может создать новую заявку на другую технику | FR-049 |
| **FO может изменить период брони до И после подтверждения**; Requestor уведомляется автоматически; повторного подтверждения не нужно | FR-048 (CONFLICT-01 **закрыт** 10.04) |
| Reminder FO — только владельцу конкретной выбранной единицы техники (не всем FO типа) | FR-NEW-23 |
| Бронирование стартует с момента **мобилизации**, не прибытия на объект | FR-NEW-18 |
| Закрытие брони — **только вручную** (кнопка); при закрытии Requestor вводит фактические start/end time | FR-NEW-32, FR-NEW-33 |
| Нет обязательного буфера между бронями | FR-NEW-19 |
| Максимальный горизонт: 30 дней (настраивается Admin) | FR-NEW-01 |
| Максимальная длительность: 7 дней (настраивается Admin) | FR-NEW-01 |
| Приоритет внутренней техники — бизнес-правило, не технически принудительное | FR-032 |

### 6.5 Поля при создании заявки

| Поле | Обязательность | Примечание |
|------|----------------|------------|
| Конкретная единица техники | ✅ | Requestor видит и выбирает единицу напрямую |
| Период (дата/время from–to) | ✅ | Начало = момент мобилизации |
| Приоритет (P1–P4) | ✅ | Requestor выбирает сам |
| Work Order # (JDE) | ✅* | Для Maintenance/Railroad/Operations флотов; 1 WO = 1 заявка |
| Location | ✅* | Для SCM Logistics флота вместо WO# (текстовый ввод) |
| Описание работ | ✅ | ~50 символов |
| Комментарий | ❌ | Опционально |
| Justification | ✅* | Только для Assigned-техники |
| Location (общая для всех позиций) | ✅ | Одна локация на заявку; время может различаться по единицам |

> **Примечание:** в рамках одной заявки все позиции имеют **одинаковую локацию**, но могут иметь **разные периоды**.

### 6.6 Отображение техники в поиске

| Ситуация | Что видит Requestor |
|----------|---------------------|
| Техника в ремонте | Серым; подпись «На ремонте до [дата из JDE]» |
| Assigned техника | Видна всем; доступна для бронирования только авторизованным |
| Shared with Conditions | Видна с цветовым маркером |
| Stationary HDE | Не отображается вообще |
| Техника добавлена в корзину другим пользователем | Конфликт-чек при отправке заявки |

**Поля в результатах поиска (обязательные):** госномер (state reg number) + TCO-номер оборудования + модель/марка (FR-NEW-38).  
**Фильтры — динамические** по типу техники; матрица «тип → фильтры» согласуется с TCO (OQ-29, ещё открыт).

## 7. Архитектура БД


### Подтверждённая модель: Order / OrderLine

**BRD v3 (раздел 5.2, 09.04) явно закрепляет архитектуру:**

> *"Data model follows Order/OrderLine pattern: one Request contains multiple RequestItems (one per equipment); each RequestItem independently processed by FO and generates a separate Booking."*

Модель «1 заявка = 1 бронь» **не соответствует BRD**. Реализуем Вариант 2.

### Структура сущностей — открытый вопрос

> ❓ **Нужна ли отдельная сущность `Booking`, если Requestor выбирает конкретную технику уже при создании заявки?**
> Предлагаем два варианта — команда разработки выбирает.

---

#### Вариант A — `RequestItem` + отдельный `Booking` (текущий дизайн)

`RequestItem` описывает потребность, `Booking` фиксирует факт подтверждённой брони. Связь 1:1, но `equipmentId` на `Booking` может отличаться от `RequestItem` (FO поменял технику).

```
RESOURCES MODULE                      BOOKING MODULE
─────────────────────────────────     ────────────────────────────────────────────
users ──────────────────────────────► requests
  │                                      │  requestorId
  │ (ownerUserIds)                        │  workOrderNumber / location
  ▼                                      │  priority, description, comments
fleets ─── (fleetId) ──► equipment       │  periodRequested { from, to }
                │               ▲        │  status (aggregate)
        equipment_types         │        │  itemCount / confirmedCount
                                │        └──► request_items[]
                                │                 │  equipmentId (запрошенная)
                                │                 │  targetFoId → users
                                │                 │  fleetId (денорм.)
                                │                 │  specificPeriod { from, to }
                                │                 │  deliveryLocation
                                │                 │  transportAssignment
                                │                 │  status (item-level)
                                │                 │  foTimeoutAt
                                │                 │  rejectionReason
                                │                 ▼
                                └────────── bookings
                                               │  requestItemId (1:1)
                                               │  requestId (денорм.)
                                               │  equipmentId (фактическая, м.б. ≠ item)
                                               │  equipmentSnapshot { model, plate, fleet }
                                               │  periodStart / periodEnd
                                               │  mobilizationStartedAt
                                               │  actualStartTime / actualEndTime
                                               │  status
                                               └──► booking_extensions
```

| | |
|---|---|
| **Плюсы** | Чёткое разделение «запрос» vs «факт»; замена техники FO не меняет историю запроса; `Booking` — единственный источник правды для проверки конфликтов |
| **Минусы** | 1:1 с `RequestItem` — дублирование данных; нужна синхронизация статусов между двумя сущностями; лишние joins |

**Коллекции:**

| Коллекция | Назначение | Модуль |
|-----------|-----------|--------|
| `users` | Пользователи + роли (синхр. с Azure AAD) | Resources |
| `fleets` | Парки техники (с именем, ownerUserIds[]) | Resources |
| `equipment_types` | Справочник типов + specSchema (динамические поля) | Resources |
| `equipment` | Единицы техники | Resources |
| `requests` | Заявки (шапка) | Booking |
| `request_items` | Позиции заявки (1 = 1 единица техники) | Booking |
| `bookings` | Подтверждённые брони | Booking |
| `booking_extensions` | Запросы на продление | Booking |
| `notifications` | История уведомлений | Booking |
| `audit_logs` | Аудит всех действий (compliance) | Booking |
| `system_settings` | Настраиваемые параметры (Admin) | Config |

**Статус-машины:**

*Request (агрегированный, вычисляется из статусов items):*
```
draft → submitted → partially_confirmed → fully_confirmed → in_progress → completed
                                        ↘ cancelled
```

*RequestItem:*
```
pending_fo → confirmed → (booking создаётся автоматически)
           → declined
           → revoked
```

*Booking:*
```
confirmed → in_progress → completed
                        → terminated (досрочное закрытие)
          → revoked
```

#### Вариант B — только `RequestItem`, без `Booking`

`RequestItem` является бронью. FO-замена техники = update поля `assignedEquipmentId` (с логом в `audit_logs`). Конфликт-проверка — запрос по `request_items`.

```
RESOURCES MODULE                      BOOKING MODULE
─────────────────────────────────     ─────────────────────────────────────────────
users ──────────────────────────────► requests
  │                                      │  requestorId
  │ (ownerUserIds)                        │  workOrderNumber / location
  ▼                                      │  priority, description, comments
fleets ─── (fleetId) ──► equipment       │  periodRequested { from, to }
                │                        │  status (aggregate)
        equipment_types                  │  itemCount / confirmedCount
                                         └──► request_items[]
                                                  │  requestedEquipmentId (выбор Requestor'а)
                                                  │  assignedEquipmentId  (м.б. изменён FO)
                                                  │  equipmentSnapshot { model, plate, fleet }
                                                  │  targetFoId → users
                                                  │  fleetId (денорм.)
                                                  │  specificPeriod { from, to }
                                                  │  deliveryLocation
                                                  │  transportAssignment
                                                  │  status
                                                  │  foTimeoutAt
                                                  │  rejectionReason
                                                  │  mobilizationStartedAt
                                                  │  actualStartTime / actualEndTime
                                                  └──► request_item_extensions
```

| | |
|---|---|
| **Плюсы** | Нет дублирования; нет синхронизации статусов; проще запросы; меньше коллекций |
| **Минусы** | `RequestItem` становится «толстым»; замена техники FO видна только через audit_log, не в структуре; история «что просили» vs «что назначили» — два поля в одной записи |

**Коллекции:**

| Коллекция | Назначение | Модуль |
|-----------|-----------|--------|
| `users` | Пользователи + роли (синхр. с Azure AAD) | Resources |
| `fleets` | Парки техники (с именем, ownerUserIds[]) | Resources |
| `equipment_types` | Справочник типов + specSchema (динамические поля) | Resources |
| `equipment` | Единицы техники | Resources |
| `requests` | Заявки (шапка) | Booking |
| `request_items` | Позиции заявки = брони | Booking |
| `request_item_extensions` | Запросы на продление | Booking |
| `notifications` | История уведомлений | Booking |
| `audit_logs` | Аудит всех действий (compliance) | Booking |
| `system_settings` | Настраиваемые параметры (Admin) | Config |

**Статус-машины:**

*Request (агрегированный, вычисляется из статусов items):*
```
draft → submitted → partially_confirmed → fully_confirmed → in_progress → completed
                                        ↘ cancelled
```

*RequestItem (единая машина, без отдельного Booking):*
```
draft → pending_fo → confirmed → in_progress → completed
                               → terminated (досрочное закрытие)
                   → declined
                   → revoked
```

> ⚠️ Точный mapping агрегированного статуса Request на статусы items — TBD (OQ-36).

### Новые поля, важные для разработчиков

| Поле | Коллекция | Обоснование |
|------|-----------|-------------|
| `mobilizationStartedAt` | `bookings` | Фиксируется кнопкой «Мобилизация началась» у FO (FR-NEW-24) |
| `actualStartTime` / `actualEndTime` | `bookings` | Вводится Requestor-ом при закрытии (FR-NEW-33); используется для аналитики утилизации |
| `equipmentSnapshot` | `bookings` | Snapshot key-полей техники на момент подтверждения (model, licensePlate, fleetName) — для истории |
| `statusHistory[]` | `requests`, `bookings` | Embedded array для быстрого timeline в UI |
| `transportAssignment` | `request_items` | Трал/буксир, добавляемый FO для Unwheeled |
| `transportationConfirmedAt` | `request_items` | Подтверждение от Transportation Responsible |
| `foTimeoutAt` | `request_items` | SLA-дедлайн на уровне позиции (не заявки целиком) |

### Рекомендации по реализации

| # | Тема | Рекомендация |
|---|------|-------------|
| 1 | **Conflict-check** | Индекс на `bookings(equipmentId, status IN [confirmed, in_progress], periodStart, periodEnd)`; проверять при создании RequestItem |
| 2 | **Soft lock** | При добавлении позиции в заявку — мягкая блокировка слота (race condition при параллельных заявках) |
| 3 | **State machine** | Реализовать как explicit state machine в backend — не просто поле. Исключить невалидные переходы |
| 4 | **TTL** | `notifications` — TTL ~90 дней; `audit_logs` — без TTL (compliance FR-102) |
| 5 | **Денормализация** | `fleetId` в `request_items` — намеренная денорм. для фильтрации; при смене FO — учесть |
| 6 | **Booking snapshot** | При создании Booking — снимок key-полей техники (подтверждено как preliminary, OQ-37) |
| 7 | **Расчёт утилизации** | `actualStartTime` / `actualEndTime` при закрытии = данные для дашборда; хранить отдельно от bookingPeriod |

#### Отчёты и аналитика

- Среднее время ответа FO (SLA-мониторинг)

Подтверждено, что Admin управляет:
