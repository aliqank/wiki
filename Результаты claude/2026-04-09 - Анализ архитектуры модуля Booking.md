## Часть 1 — Обратная связь по рассуждению

### Что правильно

| Тезис из рассуждения | Оценка |
|---------------------|--------|
| FO делает CRUD с техникой | ✅ Верно — R-55, встреча 08.04 |
| Request содержит несколько единиц техники | ✅ Верно — R-26 |
| Request хранит историю статусов (кто/когда менял) | ✅ Нужно — для audit trail |
| Booking живёт своей жизнью — один на каждую единицу | ✅ Правильная интуиция (см. ниже) |
| Booking — движение ID-шек; данные — в модуле Resources | ✅ Архитектурно верно (DDD: Booking как координирующий bounded context) |

---

### Ключевой вопрос: 1 заявка → N броней?

**Ответ: да.** Это правильная модель. Вот почему:

```
REQUEST (заявка)
  ├── общий контекст: WO#, priority, requestor, description, период
  └── REQUEST_ITEMS[] — по одному на каждую единицу техники
        ↓ (после подтверждения FO)
      BOOKING — один на один REQUEST_ITEM
        └── живёт своей жизнью: extends, in_progress, completed
```

**Почему не вкладывать items прямо в Booking:**
- Продлить можно одну конкретную бронь, не всю заявку
- Статус каждой единицы независим (одну подтвердили, другую отклонили)
- FO может заменить технику в конкретной позиции, не трогая остальные

---

### Вопрос: место, время, дата — атрибут брони или заявки?

**Ответ: оба уровня, но по-разному.**

| Атрибут | Уровень | Обоснование |
|---------|---------|-------------|
| Запрошенный период (окно) | Request | Requestor задаёт общий контекст — "мне нужна техника с X по Y" |
| Фактический период конкретной единицы | RequestItem / Booking | Может уточняться при подтверждении FO |
| Место доставки (для unwheeled) | RequestItem | Каждая единица может ехать в разное место |
| Транспорт (трал) | RequestItem | На каждую единицу — свой транспорт |

**Вывод:** период на уровне Request — это "запрошенное окно", на уровне Booking — "подтверждённые даты". Обе нужны.

---

### Что не отражено в рассуждении

1. **RequestItem как промежуточная сущность** — явно не названа, но подразумевается. Это ключевой объект: именно он связывает Request и Booking, несёт статус FO-ответа.

2. **Статус-машина на двух уровнях** — у Request агрегированный статус (`partially_confirmed`, `fully_confirmed`), у каждого RequestItem/Booking — собственный.

3. **FO timeout привязан к RequestItem**, не к Request — разные FO могут отвечать на разные позиции с разными дедлайнами.

4. **Замена техники** — FO может заменить конкретную единицу (R-48). Это изменяет `equipmentId` в RequestItem/Booking, не в Request.

5. **Модуль Resources** — хорошая интуиция, но нужно определить граница: что именно там? `users`, `equipment`, `fleets`, `equipment_types`. Booking модуль хранит только их ID + временну́ю проекцию.

## Часть 2 — Примерная структура БД

> Версия расширяет `2026-04-08 - Архитектура БД базовая.md`.
> Ключевое изменение: введена `request_items` как явная сущность.

---

### Схема сущностей (ERD)

```
RESOURCES MODULE                    BOOKING MODULE
─────────────────────────────────   ────────────────────────────────────────────

users ──────────────────────────────► requests
  │                                     │  requestorId → users
  │ (ownerUserIds)                       │  periodRequested {from, to}
  ▼                                     │  workOrderNumber
fleets ──── (fleetId) ──► equipment     │  priority, description
                │               ▲       │  status (aggregate)
        equipment_types         │       └──► request_items[]
                                │              │  equipmentId → equipment  ◄──┘
                                │              │  targetFoId → users
                                │              │  fleetId → fleets (denorm)
                                │              │  specificPeriod {from, to}
                                │              │  deliveryLocation
                                │              │  transportAssignment
                                │              │  status (item-level)
                                │              │  foTimeoutAt
                                │              │  rejectionReason
                                │              ▼
                                └──────── bookings
                                              │  requestItemId → request_items
                                              │  requestId (denorm)
                                              │  equipmentId (denorm, может ≠ item)
                                              │  requestorId, fleetOwnerId
                                              │  periodStart, periodEnd, periodEndActual
                                              │  status
                                              └──► booking_extensions
                                                       newPeriodEnd
                                                       status
```

### Статус-машины

**Request (агрегированный):**
```
draft → submitted → partially_confirmed → fully_confirmed → in_progress → completed
                                       ↘ cancelled (по решению requestor)
```

**RequestItem (по каждой позиции):**
```
pending_fo → confirmed → (→ booking создаётся)
           → rejected   (заявка не закрывается — R-34)
           → cancelled
```

**Booking:**
```
confirmed → in_progress → completed
          ↘ cancelled
```

## Часть 3 — Улучшения и рекомендации

### 1. Ввести `request_items` явно (приоритет: высокий)

В текущей `2026-04-08 - Архитектура БД базовая.md` используется подход "1 Request = 1 единица + опциональный `request_groups`". Это неудобно: `request_groups` — надстройка, а не часть основной модели.

**Рекомендация:** Request (шапка) + RequestItems (позиции). Это стандартная паттерн «Order / OrderLine» — понятен разработчикам, масштабируется.

---

### 2. Статус на двух уровнях (приоритет: высокий)

Разделить статус-машину: Request — агрегированный, RequestItem — атомарный. Это позволит:
- Показывать "3 из 5 единиц подтверждено" (R-26)
- Правильно обрабатывать частичный отказ FO (R-34: отказ не закрывает всю заявку)

---

### 3. Снимки данных в Booking (приоритет: средний)

При создании Booking — сохранять snapshot ключевых полей техники на момент подтверждения:

```json
"equipmentSnapshot": {
  "model": "CAT 320",
  "licensePlate": "A123BC",
  "fleetName": "Флот Логистики"
}
```

**Зачем:** если техника позже удалена/переименована — история броней остаётся читаемой. Это также снижает JOIN-нагрузку при отчётах.

---

### 4. StatusHistory как embedded array (приоритет: средний)

В рассуждении верно отмечено: нужно хранить "кто когда апдейтил статус". Варианты:
- **Option A:** embedded array `statusHistory[]` в Request/Booking (проще, достаточно для большинства задач)
- **Option B:** отдельная `audit_logs` коллекция (уже есть в модели)

**Рекомендация:** оба. `audit_logs` — compliance-уровень. `statusHistory[]` внутри Request — для быстрого отображения timeline в UI без JOIN.

```json
"statusHistory": [
  { "status": "submitted", "at": "...", "by": "userId", "comment": null },
  { "status": "pending_fo", "at": "...", "by": "system", "comment": null }
]
```

---

### 5. Conflict-check на уровне RequestItem, не Request (приоритет: высокий)

Проверка доступности техники: `bookings(equipmentId, status IN [confirmed, in_progress], periodStart ≤ X.periodEnd, periodEnd ≥ X.periodStart)`.

Проверять при создании RequestItem (не при создании Request-шапки).

---

### 6. Открытые вопросы для следующего шага

| # | Вопрос | Почему важно |
|---|--------|-------------|
| OQ-A | Можно ли продлить только часть броней из одной заявки? | Определяет, нужен ли `booking_extensions` на уровне Booking или RequestItem |

## Итог

Рассуждение архитектурно верное. Главная доработка — явно ввести **`request_items`** как самостоятельную сущность между Request и Booking. Это решает все открытые вопросы:
- да, 1 заявка → N броней (через items)
- да, место/время — атрибут item/booking, не шапки request
- да, каждая бронь живёт своей жизнью
- да, booking хранит только ID — данные в Resources
