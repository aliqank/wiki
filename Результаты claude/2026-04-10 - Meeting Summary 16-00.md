### Что обсуждалось по BRD

#### Глоссарий
- **Термин «Mobilization»** — уже был добавлен ранее, подтверждён.
- **Термин «Utilization»** — **добавлен**. Определение:
  - Утилизация = загруженность техники на день/месяц/год (насколько эффективно компания распоряжается техникой).
  - Tracked двумя способами: по **пробегу** (для одних типов) или по **моточасам** (для других).
  - Каждый Fleet Owner самостоятельно определяет порог 100% для своего типа техники (н-р, 2 ч/день = 100%).
  - Добавить параметр: **«Максимальная возможная утилизация в рабочую смену»** (Maximum utilization capacity per shift).

#### Роли

| Роль | Решение |
|------|---------|
| **Service Work Processor (4.2)** | Роль **не определена** — неясно, это компонент системы или пользователь. Помечена как "not defined", временно исключается из активных требований. Возврат при необходимости. |
| **Fleet Owner (4.3) — создание техники** | **Исправление:** и internal, и external FO могут создавать технику под свой парк (не только external, как было в BRD). Long-term rented заполняет внутренняя команда (не BP). |
| **Fleet Owner (4.3) — редактирование периода после подтверждения** | **CONFLICT-01 ЗАКРЫТ:** FO может редактировать период бронирования **в том числе после confirmation**. Requestor получает уведомление; повторное подтверждение не требуется. Причина: погодные условия, перенос работ; Requestor может быть на объекте без доступа к ПК. |
| **CC Owner (4.4)** | **Подтверждено:** Long-term rented — внутренний флоу без CC Owner. Пункт 44 исключается |

#### Сущности

**Fleet / Парк:**
- Флиты должны иметь **имена** (не только номера).
- Пример группировки: Heavy Ops, Logistics, Maintenance, Production и т.д.
- Один FO может управлять несколькими флитами / группами техники.
- Привязка техники — к **конкретному сотруднику** (не к отделу); при смене сотрудника — Admin обновляет вручную.
- Номер техники: уникальный 6-значный show-number (не повторяется).

**Equipment card (карточка техники):**
- Поле `etc.` в Basic fixed info — **нужно конкретизировать**. Решено: на следующей встрече разобрать по типам техники.
- Запланировано: команда подрядчика готовит макет карточки техники, TCO уточняет поля.

**Regular Request:**
- Уточнение: минимум **1** единица техники в заявке (не 2+, как было указано ранее; "2+" относилось к другому контексту).
- Поля в форме: Work Order (обязательное для Maintenance/Railroad/Ops), Location (для SCM Logistics), Work Description (~50 символов), Comments (опционально), Priority (P1–P4).
- Один WO = одна заявка; в рамках одного WO — одинаковая локация, время может различаться по единицам техники.

**Booking:**
- External on-demand (BP showcase): исключён из booking flow, только витрина.
- Long-term rented: **внутренний** флоу (не external).

**Admin (4.5) — Manage Templates (пп. 7 и 8):**
- Уточнено: предположительно подразумевается возможность кастомизировать поля форм заявок и карточек техники без участия разработчиков.
- **Решение:** отложить детализацию до готовности прототипа форм; пункты помечены как TBD.

**Shared with Conditions vs. Shared without Conditions:**
- Вопрос: если любую заявку можно досрочно закрыть — нужно ли деление?
- **Решение:** оставить поле, вернуться к вопросу позже.
