# UC-REQ-08 - Оставление отзыва по технике в рамках брони

**Created:** 2026-06-09  
**Last updated:** 2026-06-09  
**Автор документов:** OpenCode

## Карточка use case

| Поле | Значение |
|---|---|
| Область действия | Страница `Мои заявки` / detail view заявки / detail view конкретной брони |
| Участник | Пользователь с ролью [`Requestor`](../../Roles and Access Model.md) или [`ServiceWorkProcessor`](../../Roles and Access Model.md) |
| Покрываемые FR (BRD) | `FR-022` |
| Покрываемые FR (Additional list) | — |
| Предусловие | Пользователь авторизован; пользователь имеет доступ к брони; бронь достигла `Confirmed` и выше; у брони есть связанная техника (`equipmentId`) |
| Триггер | Нажатие кнопки `Оставить отзыв` / `Leave feedback` в карточке брони |
| Ожидаемый результат | Система сохраняет feedback по технике, привязанный к конкретной брони и технике, и возвращает созданную запись |
| Используемые API | [`POST /bookings/{id}/feedback`](../../../api/booking/requestor/POST_bookings_id_feedback.md) |

---

## Основной сценарий

1. Пользователь открывает страницу `Мои заявки` или detail view заявки.
2. Пользователь переходит в карточку нужной брони.
3. Frontend показывает контекст брони:
   - номер заявки;
   - технику;
   - текущий статус брони;
   - текущий период использования.
4. Если бронь находится в допустимом статусе, система показывает действие `Оставить отзыв`.
5. Пользователь нажимает `Оставить отзыв`.
6. Frontend открывает форму ввода feedback.
7. Пользователь вводит текст отзыва по использованной технике.
8. Frontend вызывает [`POST /bookings/{id}/feedback`](../../../api/booking/requestor/POST_bookings_id_feedback.md).
9. Backend проверяет, что:
   - бронь существует;
   - пользователь имеет доступ к брони;
   - бронь достигла `Confirmed` и выше;
   - у брони есть `equipmentId`;
   - текст feedback непустой.
10. Backend создает запись в `EquipmentFeedbacks`.
11. Backend возвращает созданный feedback с `id`, `bookingId`, `equipmentId`, `feedback`, `createdAt`.
12. Frontend показывает пользователю успешный результат сохранения.

---

## Альтернативные сценарии

1. Бронь уже находится в статусе `InProgress`.
   Пользователь все равно может оставить feedback, так как метод разрешен для брони, достигшей `Confirmed` и выше, и feedback сохраняется без изменения статуса брони.

2. Пользователь хочет оставить feedback при завершении работ.
   Feedback выполняется как отдельное действие до или после close-flow через тот же [`POST /bookings/{id}/feedback`](../../../api/booking/requestor/POST_bookings_id_feedback.md), а не как часть `POST /bookings/{id}/close`.

3. Пользователь не авторизован.
   Backend возвращает `UNAUTHORIZED`.

4. Пользователь не имеет доступа к брони.
   Backend возвращает `FORBIDDEN`.

5. Бронь не найдена.
   Backend возвращает `NOT_FOUND`.

6. Статус брони пока не позволяет оставить feedback.
   Backend возвращает `BOOKING_FEEDBACK_NOT_ALLOWED`.

7. У брони отсутствует связанная техника.
   Backend возвращает ошибку бизнес-валидации / conflict according to backend implementation.

8. Текст feedback пустой.
   Backend возвращает `VALIDATION_ERROR`.

---

## Замечания

1. Use case описывает feedback по технике, а не отдельный booking comment flow.
2. Feedback относится к технике, но создается в контексте конкретной брони и потому должен быть связан и с `bookingId`, и с `equipmentId`.
3. Feedback не меняет lifecycle status брони.
4. Сценарий должен быть доступен во время `InProgress`, то есть не только после завершения работ.
5. Если пользователь завершает работы и хочет сделать и `Close booking`, и `Leave feedback`, UI может показать эти действия рядом, но это должны быть два отдельных backend calls.
