# UC-REQ-01.1 - Просмотр одной заявки

**Created:** 2026-06-05  
**Last updated:** 2026-06-05  
**Автор документов:** Telman Nurzhanov (SA)

---

## Карточка use case

| Поле | Значение |
|---|---|
| Область действия | Страница `Мои заявки` -> detail view / экран `Новая заявка / Редактировать заявку` для одной заявки |
| Участник | Пользователь с ролью [`Requestor`](../../Roles%20and%20Access%20Model.md) |
| Покрываемые FR (BRD) | `FR-024`, `FR-025`, `FR-026`, `FR-038`, `FR-039`, `FR-041` |
| Покрываемые FR (Additional list) | `BRD-U-001` |
| Предусловие | Пользователь авторизован в системе; пользователь имеет роль [`Requestor`](../../Roles%20and%20Access%20Model.md); заявка принадлежит текущему пользователю; пользователь уже выбрал конкретную заявку из списка `Мои заявки` |
| Триггер | Открытие detail view конкретной заявки |
| Ожидаемый результат | Пользователь видит полное текущее состояние одной заявки, включая request-level поля и расширенные карточки всех booking item-ов |
| Используемые API | [`GET /booking-requests/{id}`](../../../api/booking/requestor/GET_booking_requests_id.md) |

---

## Основной сценарий

1. Пользователь открывает страницу `Мои заявки`.
2. Пользователь выбирает одну конкретную заявку из списка.
3. Frontend получает `requestId` выбранной заявки.
4. Frontend вызывает [`GET /booking-requests/{id}`](../../../api/booking/requestor/GET_booking_requests_id.md).
5. Backend проверяет, что:
   - заявка существует;
   - текущий пользователь является ее `requestor`;
   - пользователь имеет право просмотра этой заявки.
6. Backend возвращает полную агрегированную модель заявки.
7. Frontend отображает header заявки:
   - заголовок страницы;
   - номер заявки.
8. Frontend отображает request-level sidebar:
   - `Default Work Order`;
   - `Work Order`;
   - `Priority`;
   - `Location`;
   - `Описание работ`;
   - `Комментарий`.
9. Frontend отображает список booking item-ов как отдельные карточки.
10. Для каждой карточки брони пользователь видит:
   - фото техники;
   - title / display name техники;
   - базовый equipment context;
   - идентификаторы техники (`TCO`, `ГРНЗ`);
   - work center;
   - booking period;
   - текущую availability / conflict информацию;
   - dynamic properties;
   - justification, если оно требуется или уже заполнено.
11. Пользователь использует detail view как основной экран просмотра и последующего редактирования / отправки заявки.

## Альтернативные сценарии

1. Заявка не найдена.
   Backend возвращает `NOT_FOUND`; frontend показывает сообщение об ошибке.

2. Пользователь пытается открыть чужую заявку.
   Backend возвращает `FORBIDDEN`.

3. У заявки нет броней.
   Frontend показывает request-level данные и пустое состояние списка техники.

4. У одной или нескольких броней есть конфликт по периоду.
   Frontend показывает warning / conflict presentation на соответствующей карточке, но detail view заявки в целом все равно открывается.

5. Для брони требуется транспортировка или special handling.
   Frontend показывает дополнительный informational / warning block на карточке брони.

## Замечания

1. Сценарий является дочерним по отношению к `UC-REQ-01 - Просмотр моих заявок` и описывает именно detail view одной заявки.
2. Просмотр одной заявки должен использовать полный detail API, а не только summary-данные списка `Мои заявки`.
3. Request-level и booking-level данные должны возвращаться одним агрегированным response, достаточным для открытия экрана без серии дополнительных read-call-ов на каждый booking item.
4. Booking item в detail view отображается как расширенная UI-card, а не как плоская строка.
5. Конфликтность брони, состояние техники и transport-related warnings должны отображаться на уровне карточки конкретной брони.
6. Наличие конфликтов или ограничений не мешает просмотру заявки; они являются частью информационного контекста detail view.
