## Карточка use case

| Поле | Значение |
|---|---|
| Область действия | Страница `Мои заявки` |
| Участник | Пользователь с ролью `Requestor` или `ServiceWorkProcessor` |
| Покрываемые FR (BRD) | `FR-025`, `FR-091` |
| Покрываемые FR (Equipment block list) | — |
| Предусловие | Пользователь авторизован в системе; пользователь находится на странице `Мои заявки`; пользователь имеет роль `Requestor` или `ServiceWorkProcessor` |
| Триггер | Вход на страницу `Мои заявки` |
| Ожидаемый результат | Отображается список незавершенных заявок текущего пользователя с краткой информацией по броням |
| Используемые API | `GET /booking-requests/my`, `GET /booking-requests/{id}` |

---

## Основной сценарий

1. Пользователь открывает страницу `Мои заявки`.
2. Frontend вызывает `GET /booking-requests/my`.
3. Backend возвращает только незавершенные заявки текущего пользователя.
4. Frontend отображает список заявок в таблице.
5. Для каждой заявки отображаются:
   - номер заявки;
   - дата создания;
   - данные реквестора;
   - номер Work Order;
   - приоритет;
   - краткий список броней.
6. Для каждой брони в summary-блоке отображаются:
   - тип техники;
   - марка / модель;
   - номер ТШО;
   - ГРНЗ;
   - work center;
   - владелец;
   - плановый диапазон брони;
   - фактический диапазон брони;
   - статус.
7. При выборе конкретной заявки frontend может открыть детальный просмотр через `GET /booking-requests/{id}`.

---

## Альтернативные сценарии

1. У пользователя нет незавершенных заявок.
   Система отображает пустое состояние и кнопку `Создать заявку`.

2. Пользователь применяет фильтры.
   Frontend повторно вызывает `GET /booking-requests/my` с query-параметрами фильтрации.

3. Backend возвращает ошибку авторизации или доступа.
   Frontend отображает сообщение об ошибке и не показывает данные таблицы.

4. Пользователь открывает карточку конкретной заявки.
   Frontend вызывает `GET /booking-requests/{id}` и отображает detail view.

---

## Замечания

1. Use case опирается на правило: страница `Мои заявки` показывает только active / non-terminal requests.
2. История завершенных заявок должна быть вынесена в отдельный flow / отдельный endpoint.
3. `GET /booking-requests/my` должен возвращать summary-данные, а не полные booking details.
